# 超时降级机制

> 多 AI 协作最常见、也最危险的问题是：**一个 AI 不响应，整个流程卡死。** 本机制不用"约定时效"这种靠不住的办法，而是设计一套确定性兜底策略。

## 为什么不能用"约定时效"

很多人第一反应是"让每个 AI 约定在 X 小时内回复"。这在工程上不成立：**AI 的启动由外部调度器决定**，它无法自主"保证"某个时间在不在线。"约定时效"是想用一个运营手段解决基础设施可靠性问题，方向错了。

正确方向：**接受"AI 可能不响应"这个现实，为它设计降级路径。**

## 降级规则

```
第一层：目标 AI 在 T1（如 12 小时）内未响应
    → 由下游 AI 自行评估当前方案并继续
    → 在协作区标记 "该AI本轮未参与"

第二层：同一 AI 连续 N 次（如 3 次）超时
    → 将该 AI 标记为 "暂不可用"
    → 协作自动降级为去掉该角色的模式（如 4 人变 3 人）
    → 通知协调者评估是否要换人设/换工具/停用
```

## 关键点

| 设计点 | 说明 |
|--------|------|
| 确定性而非靠"商量" | 超时是**自动触发**的规则，不是"提醒一下再等等" |
| 超时要有阈值和上限 | 否则"等一个 AI"会无限拖延 |
| 标记可回溯 | 每次降级都在协作区留痕，事后能看是谁、为何导致降级 |
| 不因超时崩溃 | 主流程始终有"继续向前"的路径 |

## 触发条件怎么写

写清楚两个参数即可，其他地方无需改动：

```
T1      超时阈值（首次未响应的容忍时长）
N       连续超时多少次触发"下线"
```

## 使用场景

- 某个 AI 依赖外部数据源，数据源暂不可用 → 超时降级，不让它阻塞整体
- 某个角色本周没被调度到 → 不阻塞，直接按缺员模式跑
- 关键决策被卡 → 走仲裁（见 `digital-twin-pattern/arbitration-mechanism.md`）而非无限等待

## 验证标准

在启用这套机制时问自己两个问题：

- [ ] 我的工作流里存在"必须某个 AI 实时响应才能继续"的环节吗？
- [ ] 如果没有这个 AI 参与，异步/降级模式能否处理 80% 以上的场景？

如果答案是"异步已经够用"，那就**不要进入更重型的实时协作平台**——那是在为不需要的能力投入工程。详见主 README 的分阶段路径。
